How the registered devices are drawn

Three layouts for one block: the devices registered with the RomM server for save-file sync. Everything else on the page is identical across the three so the comparison is about the block alone. Switch above. B was chosen.

Width
The panel is 854 px and the content 806 px. The section list takes 264 px, leaving about 530 px for the detail pane. Drawn on the same stage as the other studies, 854 × 534.
Height
The scarce axis. The Library study measured about 263 px of body — but with a tab row. Settings has no tabs and gets that height back. What hangs below the fold is still reachable only by moving focus.
The facts per device
The server answers with five: name, client, client version, platform, last seen — plus an id and the “this device” mark.
What the client column holds
The rows above are the mix a real listing carries: this plugin registers as Tender since the rename, RomM keeps what earlier versions wrote under decky-romm-sync, and RomM's own frontend registers web. Those older rows do not expire, which is why the column is sized for the longest of the three rather than for today's name.
Why it was a question at all
The Tables rule asks for aligned columns, because a device row carries more than two facts. But every other row in this pane is a Steam Field — label left, value right — so a grid here is the only content on the page in a second visual language.
